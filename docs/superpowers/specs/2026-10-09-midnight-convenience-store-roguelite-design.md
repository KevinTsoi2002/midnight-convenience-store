# 《凌晨 2:17 的便利店》Roguelite 扩展设计规格

**日期：** 2026-10-09
**状态：** 用户已确认，进入实现计划阶段
**交付形式：** 继续保持单个可直接打开的 HTML 文件

## 1. 目标

把现有三位顾客的叙事微游戏扩展成一局约 5～10 分钟的轻 Roguelite 夜班游戏。玩家在三天夜班中服务随机顾客，依据当晚表现获得饰品，在有限装备槽中形成策略，并面对逐日增加的判断压力。

核心体验保持不变：读懂顾客，挑选三件商品，观察反馈。新增系统应该让每一局略有不同，同时保持离线、单文件、无需账号和无需后端。

## 2. 一局结构

一局最多三天：

```text
开始新一局
  -> 第 1 天：3 位顾客
  -> 当日结算：表现评价与饰品三选一
  -> 第 2 天：4 位顾客
  -> 当日结算：表现评价与饰品三选一
  -> 第 3 天：5 位顾客与特殊事件
  -> 最终结局
```

第一天建立规则认知，第二天引入隐藏需求和事件，第三天检验饰品组合。第一版不开放无限天数，避免流程失去终点，也控制单文件代码和测试规模。

## 3. 时间系统

页面加载时读取本机时间，用于首屏、顶部时钟和首张小票：

```js
const realNow = new Date();
const realClock = realNow.toLocaleTimeString("zh-CN", {
  hour: "2-digit",
  minute: "2-digit",
  hour12: false
});
```

游戏内部使用稳定的叙事时间轴，不受玩家电脑时间影响：

| 天数 | 游戏时间 |
|---|---|
| 第 1 天 | 02:17 |
| 第 2 天 | 03:06 |
| 第 3 天 | 04:12 |

首屏根据现实时间段显示一条氛围文案，但不改变主视觉：

| 现实时间 | 文案方向 |
|---|---|
| 06:00–11:59 | 城市醒了，昨晚的事还没有完全结束。 |
| 12:00–17:59 | 白天也有人把心事带进便利店。 |
| 18:00–23:59 | 夜班还没有开始，但灯已经提前亮了。 |
| 00:00–05:59 | 这个时间，只有还没睡的人知道。 |

## 4. 随机顾客

顾客从带权池中抽取。每天不重复；前一天出现过的顾客在下一天降低权重；第三天可以出现特殊顾客。随机结果必须由本局种子驱动，方便复现和测试。

顾客模型：

```js
{
  id,
  name,
  role,
  lines,
  needs,
  hiddenNeeds,
  avoidTags,
  basePatience,
  preferredProducts,
  response,
  weight,
  dayRange
}
```

第一天的需求提示清楚；第二天至少有一个隐藏需求；第三天允许同时存在表面需求和隐藏需求。每一天至少包含一种与前一天不同的需求方向，避免抽到内容高度重复的一晚。

## 5. 每日事件

每晚抽取一个轻量事件，事件只改变当晚规则，不打开复杂支线。事件在当天开场卡中显示。

第一版事件池包含：

- **雨突然变大：** `comfort` 与 `practical` 标签在评分中更重要。
- **冰柜短暂断电：** `milk` 与 `hot-food` 当晚不可选。
- **广播里有人找猫：** `company` 标签的选择获得额外权重。
- **店里只剩一盏灯：** `light` 商品可以替代一次隐藏需求。
- **老顾客回来了：** 前一天与该顾客的选择会影响本轮反馈。
- **外卖高峰：** 第二、三天的第一位顾客耐心更低，但 `energy` 需求更明显。

事件不得让一轮变成不可完成状态。缺货事件至少保留六件可选商品。

## 6. 饰品系统

每个饰品有品质、标签和规则效果。饰品不采用单纯的百分比加分，而是改变线索、容错、选择限制或事件处理方式。

品质：

```text
普通：灰绿
稀有：蓝绿
史诗：珊瑚
传说：暖金
```

装备结构：

- 饰品背包最多 8 件。
- 同时装备 3 件。
- 每晚结算后从 3 个候选饰品中三选一。
- 候选池包含一件贴合当前表现、一件补足弱点、一件高风险高收益饰品。
- 选择后可直接装备；装备满时必须替换一件或放入背包。

首批饰品至少包含 12 件，覆盖以下方向：

| 饰品 | 品质 | 效果方向 |
|---|---|---|
| 收银台上的旧硬币 | 普通 | 每晚第一次 0 分视为 1 分 |
| 暖黄灯泡 | 普通 | 选择 `warmth` 商品时显示更明确的反馈 |
| 店员围巾 | 普通 | `comfort` 商品额外保留一次容错 |
| 雨夜便签 | 稀有 | 每晚一次显示顾客一个隐藏标签 |
| 不合时宜的薄荷糖 | 稀有 | `energy` 选择让下一位顾客多显示一条线索 |
| 旧店员名牌 | 史诗 | 每天第三位顾客的最低评分提升一级 |
| 会发光的钥匙 | 传说 | 每天第一次选择时点亮一个正确需求 |

其余饰品补足 `company`、`light`、`practical`、`patience`、`clarity`、`risk` 标签，最终总数控制在 12～16 件。

推荐构筑方向：

- **暖灯流：** 关注 `warmth` 与 `comfort`，提供稳定容错。
- **观察流：** 关注 `clarity` 与 `company`，显示隐藏线索。
- **冒险流：** 关注 `risk` 与 `energy`，高分更高但低分惩罚更明显。

套装效果只做少量明确组合，不超过 3 组，避免玩家需要记忆长规则表。

## 7. 品质与结算

每日结算展示：

- 当日顾客数量
- 帮助率
- 平均评分
- 隐藏需求命中数
- 连续帮助次数
- 事件处理结果
- 下一件饰品的品质区间

品质由表现决定，具体饰品在对应品质池中随机：

```js
qualityScore =
  dayBonus + averageRoundScore + hiddenNeedHits + streakBonus + eventBonus;
```

建议区间：

| 结算分 | 品质候选 |
|---|---|
| 0–2 | 普通 |
| 3–5 | 普通 / 稀有 |
| 6–7 | 稀有 |
| 8+ | 稀有 / 史诗 |
| 第 3 天高表现 | 有机会出现传说 |

结算先展示评价，再展示候选饰品。玩家确认饰品后才进入下一天，避免奖励被快速跳过。

## 8. 难度曲线

### 第 1 天

- 3 位顾客。
- 每位顾客有 2 个主要需求。
- 台词线索清楚。
- 没有隐藏需求。
- 事件效果温和。

### 第 2 天

- 4 位顾客。
- 至少一个隐藏需求。
- 顾客出现轻微矛盾台词。
- 可能出现缺货或耐心变化。
- 饰品组合开始影响解题方式。

### 第 3 天

- 5 位顾客。
- 顾客同时有表面需求和隐藏需求。
- 出现特殊顾客或高压事件。
- 需求提示减少，但仍保留可推断线索。
- 结局同时参考表现、隐藏需求和饰品协同。

难度只增加判断压力，不通过降低点击时间或制造反应速度挑战来增加难度。

## 9. 结局

保留现有三个结局，并增加两个 Roguelite 结局：

1. **今晚的灯一直亮着：** 高帮助分，至少完成一次隐藏需求。
2. **雨停了，但店里还有人：** 中等帮助分，构筑稳定但仍有遗漏。
3. **打烊之前，请再坐一会儿：** 低帮助分，未形成明确照顾方向。
4. **这盏灯不是一个人点亮的：** 高帮助分，触发饰品协同效果。
5. **明天还会有人来：** 三天完成但表现波动明显，没有完全放弃。

不使用传统 Game Over。低表现通过灯光状态、顾客反馈、饰品品质和最终文案体现，玩家始终可以走完三天。

## 10. 状态与模块边界

继续使用单 HTML 文件，但把逻辑拆成明确的数据区、纯规则函数、渲染函数和事件绑定区。

状态扩展为：

```js
const state = {
  screen: "intro",
  day: 1,
  maxDays: 3,
  customerIndex: 0,
  dailyCustomers: [],
  currentEvent: null,
  selectedProductIds: [],
  roundScores: [],
  dailyScores: [],
  hiddenNeedHits: 0,
  streak: 0,
  inventory: [],
  equippedTrinkets: [],
  trinketChoices: [],
  runSeed: null,
  realStartTime: null,
  realClock: "",
  gameClock: "02:17",
  audioEnabled: false,
  showFeedback: false,
  showDailySettlement: false,
  showTrinketReward: false,
  screenBeforeOverlay: "game"
};
```

新增纯函数：

```js
createRun()
getRealClock()
getNightClock(day)
buildDailyCustomers(day, seed)
drawNightEvent(day, seed)
scoreSelection(customer, selectedIds, trinkets, event)
getDailySettlement(state)
getTrinketQuality(settlement, day)
drawTrinketChoices(quality, state)
applyTrinket(state, trinketId)
getDifficulty(day)
getRunEnding(state)
```

随机函数使用本局种子，不使用不可测试的直接 `Math.random()` 作为业务规则来源。视觉动画和音效仍可使用实时随机性，但不得改变结算结果。

## 11. 页面与交互

新增三个界面状态：

### 夜班开场卡

显示：

- 现实时间
- 第几天与游戏时间
- 今晚事件
- 当前装备饰品
- 开始营业按钮

### 当日结算页

显示：

- 今日小票摘要
- 帮助率与隐藏需求命中
- 灯光状态变化
- 品质区间提示
- 继续抽取饰品按钮

### 饰品选择页

显示三张品质明确的饰品卡，包含名称、效果、标签和装备状态。选择后出现替换确认或放入背包提示。

移动端使用纵向排列，饰品卡保持固定最小高度，不能出现文字遮挡或横向溢出。桌面端沿用现有双栏视觉系统，不增加卡片嵌套。

## 12. 容错与持久化

- 单局状态只保存在内存中，刷新页面即开始新局。
- 不引入登录、联网存档或远程 API。
- 浏览器不支持音频时不影响结算与饰品选择。
- 随机种子保存于当前状态，测试可注入固定种子。
- 缺货事件始终保留至少六件商品可选。
- 饰品效果在渲染前统一归一化，重复装备不产生未定义叠加。

## 13. 验收标准

1. 直接打开单 HTML 可以开始一局三天夜班。
2. 首屏和顶部时钟读取并显示本机当前时间。
3. 每天顾客顺序由种子驱动的随机池生成，同一天不重复。
4. 每轮结束进入反馈，再进入当日结算。
5. 每日结算根据表现给出品质区间，并提供三个饰品候选。
6. 玩家最多装备三个饰品，背包最多保存八件。
7. 第二天和第三天的顾客数、隐藏需求和事件压力递增。
8. 三天完成后至少可以触发五种结局中的三种。
9. 刷新或重新开始不会残留上一局状态。
10. 320～1440px 无横向溢出，新增结算和饰品页面无重叠。
11. 无外部运行时依赖或网络请求。
12. 现有核心流程、音频降级和键盘焦点测试继续通过。

## 14. 明确不做

- 无限天数和永久成长。
- 金币、商店、复杂合成或装备强化。
- 实时倒计时、反应速度挑战。
- 联网排行榜、账号和云端存档。
- 在线 AI 顾客对话。
- 超过 16 件饰品或超过 8 个每日事件。
